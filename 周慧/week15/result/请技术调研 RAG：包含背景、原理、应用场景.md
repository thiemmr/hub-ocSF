## 技术名称

RAG（Retrieval-Augmented Generation，检索增强生成），别名包括"检索增强生成""检索式增强生成""RAG 架构"，在工业界常与"知识库问答""企业级 LLM 应用"等概念绑定出现。核心思想一句话：让大模型在生成回答前，先从外部知识库中检索相关信息，再基于这些信息生成答案。

## 技术背景

大语言模型（LLM）有一个致命短板：它的知识被"冻结"在训练数据里，存在"知识截止日期"，无法感知训练之后的新信息，也无法访问私有知识库，而且面对专业领域问题时容易一本正经地"编造"（幻觉）。直接让 LLM 回答这些问题，要么答错，要么答"我不知道"。RAG 的出现就是为了解决这个痛点——它把"检索"和"生成"两件事拼在一起，让模型在回答前先去外部知识库里"查资料"，再基于查到的资料作答。这样既不用重新训练模型（避免每次更新知识都要重新训练的高昂成本），又能让回答带上最新、最准确的依据，实现知识的实时更新和事实性增强。

## 技术原理

这是本报告的核心，我尽量讲透。

**整体思路：先查后答，把"记忆"外置**

你可以把 RAG 理解成一个"开卷考试"的考生。传统 LLM 是"闭卷考试"——所有知识都装在脑子里（参数里），考到没学过的就瞎编。RAG 让这个考生在答题前先翻一本指定的参考书（外部知识库），把相关段落抄到草稿纸上，再照着草稿纸组织答案。这个"翻书—摘抄—作答"的过程，就是 RAG 的三段式流水线：**索引（Indexing）→ 检索（Retrieval）→ 生成（Generation）**。

**第一阶段：索引（离线准备，把知识库变成可搜索的"目录"）**

这一步在用户提问之前就做好了，核心是"把文档变成向量"。

1. **文档加载与切分（Chunking）**：原始文档（PDF、网页、数据库记录）先被读进来，然后切成一个个小块（chunk）。为什么要切？因为后面要把每块文本转成向量，而向量模型对输入长度有限制，且过长的块会稀释语义。切分策略很讲究：按固定字符数切最简单，但容易把一句话拦腰截断；更聪明的做法是按段落、按语义边界切，甚至用递归字符切分器（RecursiveCharacterTextSplitter）先按段落、再按句子逐级切，保证每块语义相对完整。块的大小（chunk size）和块间重叠（overlap）是调参重点——块太小语义不全，块太大检索不精准。实践中通常每块 200~500 个 token。

2. **向量化（Embedding）**：用嵌入模型（如 OpenAI 的 text-embedding-3、开源的 BGE、M3E 等）把每个 chunk 编码成一个高维向量（比如 1024 维）。这个向量的神奇之处在于：语义相近的文本，向量在空间里也靠得近。比如"猫生病了"和"猫咪不舒服"的向量距离就很近，尽管字面完全不同。

3. **构建向量索引（Vector Index）**：把所有 chunk 的向量存进向量数据库（如 FAISS、Milvus、Pinecone、Chroma）。为了加速检索，还会建立特殊的数据结构，比如 HNSW（分层可导航小世界图）或 IVF（倒排文件索引）。你可以把 HNSW 理解成一张"高速公路网"——先通过粗粒度节点快速定位到大致区域，再在局部细找，这样几百万条向量也能在毫秒级内完成搜索。

**第二阶段：检索（在线查询，从目录里找最相关的几段）**

用户提问时，系统做两件事：

1. **问题向量化**：把用户的问题也用同一个嵌入模型转成向量。
2. **相似度搜索**：在向量数据库里做"相似度搜索"（通常是余弦相似度或内积），找出与问题向量最接近的 Top-K 个文档块（比如最相关的 5 段）。

关键点：这里找的是"语义相似"而非"关键词匹配"，所以即使用户问法和文档写法不同，也能找到相关内容。比如用户问"去年营收多少"，即使文档里写的是"2023 年度财务表现"，也能被检索到。你可以类比为：你拿着问题去仓库，仓库管理员按"意思最接近"帮你抽出最相关的几张卡片。

**第三阶段：生成（Generation）——"看着卡片作答"**

把检索到的文档块和用户问题拼接成一个 Prompt，格式通常是：

```
根据以下资料回答问题：
[资料1]...
[资料2]...
问题：...
回答：
```

把这个 Prompt 交给 LLM，LLM 基于这些资料生成答案，并可以要求它标注引用来源（如"根据文档第 3 页"）。这一步的关键是：**答案被"约束"在检索到的资料范围内**，从而大幅降低幻觉。类比：你拿着抽出来的卡片，照着卡片内容组织语言回答，而不是凭记忆瞎编。

**为什么这样设计？** 核心在于"记忆外置"和"检索与生成解耦"。LLM 的参数是固定的，你无法低成本地往里面塞新知识；但向量数据库可以随时增删改。所以 RAG 把"知识存储"从模型参数中剥离出来，模型只负责"理解与表达"，知识库负责"事实供给"。知识更新只需替换向量库里的文档（不用重新训练模型），回答有据可查（降低幻觉）。你可以理解为：RAG 给 LLM 装了一个"实时联网的知识外挂"——LLM 是聪明的实习生，RAG 是给这个实习生配了一个随时可查的公司档案室。

## 应用场景

**该用的场景**：

- **企业知识库问答（最主流）**：比如公司内部规章制度、产品手册、客服 FAQ。文档经常更新，用 RAG 只需定期更新向量库，无需重训模型。案例：某大型银行把内部规章制度、产品手册、合规文件做成 RAG 系统，员工提问"大额转账的审批流程是什么"，系统检索相关制度文档并给出带条款引用的答案。
- **实时信息查询**：比如新闻摘要、股票行情解读、政策解读——这些信息变化快，模型训练数据永远跟不上，RAG 可以接入实时数据源。
- **私有数据问答**：模型训练时根本没见过你的私有数据（如企业内部报表、医疗病历、法律卷宗），RAG 让模型能"查阅"这些数据而不泄露到训练集。
- **要求答案可溯源的场景**：比如医疗建议、法律咨询、金融合规——需要回答附上"依据来源"，RAG 天然支持引用。

**不该用的场景**：

- **纯创意生成**：比如写诗、编故事、头脑风暴——不需要事实依据，RAG 反而会限制模型的创造力。
- **简单常识问答**：比如"太阳从哪边升起"——模型本身就会，检索反而增加延迟和复杂度。
- **对延迟极度敏感的场景**：RAG 多了一步检索，会增加几百毫秒到几秒的延迟。如果要求毫秒级响应，可能不适合。
- **知识库质量差**：如果文档本身混乱、过时、互相矛盾，RAG 会把"垃圾"检索出来喂给模型，效果比不用 RAG 还差。

## 缺点与对比

**RAG 的固有缺陷**：

1. **检索质量是天花板**：如果检索器没找到相关文档，生成器再强也白搭。检索召回率不高时，回答质量断崖式下跌。
2. **上下文窗口限制**：检索到的 Top-K 文档块可能超出 LLM 的上下文长度，需要截断或压缩，可能丢失关键信息。
3. **切分粒度两难**：块太小语义不全，块太大检索不精准，且容易混入无关信息。
4. **延迟增加**：相比直接调用 LLM，RAG 多了一次向量检索（和可能的重排序），端到端延迟更高。
5. **维护成本**：需要维护文档切分策略、嵌入模型、向量数据库、检索参数等多个组件，系统复杂度高于纯 LLM 调用。

**与同类技术的对比**：

| 对比维度 | RAG | 微调（Fine-tuning） | 长上下文窗口（Long Context） |
|---------|-----|---------------------|---------------------------|
| 知识更新 | 只需更新向量库，秒级生效 | 需要重新训练，成本高、周期长 | 无需更新，但受限于模型窗口 |
| 幻觉控制 | 较好，答案被约束在检索资料内 | 中等，模型仍可能编造 | 较弱，资料太长时模型会"遗忘"中间内容 |
| 私有数据支持 | 天然支持，数据不进模型参数 | 需要数据参与训练，有泄露风险 | 需要把数据塞进 prompt，受窗口限制 |
| 成本 | 需要向量数据库和检索基础设施 | 训练成本高（GPU、数据标注） | 推理成本随上下文长度线性增长 |
| 适用场景 | 知识频繁更新、要求可溯源 | 模型风格/能力定向调整 | 单次输入超长文档（如整本书） |
